# WINTECH 문서편집기 v5 계획 (Rust 전체 전환)

v5는 서버(지금의 Spring Boot + PDFBox, Java 25)를 **Rust로 새로 만들고**, 프로그램을 브라우저 탭이 아닌 **자기 창**으로 실행합니다.
화면(React)과 한글 편집기(rhwp, 이미 Rust/WASM)는 그대로 가져갑니다. 목표는 네 가지입니다.

| 불편 | v5 목표 |
|---|---|
| 느림 | 켜기 1초 안쪽, 큰 문서 열기·썸네일이 v4보다 눈에 띄게 빠름, 메모리 절반 이하 |
| 설치 문제 | Java 없이 실행 파일 하나 중심(설치 파일 v4 106MB → 목표 60MB 안팎), 본체 누락 같은 실패를 막고 알림 |
| 화면이 복잡함 | 자주 쓰는 일은 한눈에, 나머지는 정리해서 한 단계 안에 |
| 프로그램 창 | 자기 창·작업 표시줄 아이콘·트레이로 실행 |

## 위험과 대응 (먼저 알고 시작)

- Rust에는 PDFBox만큼 편집 기능이 갖춰진 PDF 도구가 없습니다. 특히 **원래 글꼴 그대로 글자 고치기**와 **개인정보 실제 삭제**는
  직접 만들어야 하는 부분이 많아 가장 오래 걸리고, 처음에는 v4보다 못할 수 있습니다. 전체 기간은 몇 달 단위로 봅니다.
- 그래서 **v4를 계속 쓰면서 v5를 옆에서 만듭니다.** v4는 전환 전까지 지금처럼 고치고 릴리스합니다.
- 기능마다 **v4와 같은 결과인지 자동 비교**(같은 PDF를 넣어 v4와 v5의 출력·화면 그림을 비교)하고, v4의 테스트를 Rust로 옮겨
  통과해야 그 기능을 끝난 것으로 봅니다.
- **점검 지점:** 3단계 뒤(편집 엔진 시제품)에 글자 편집 품질을 보고 계속할지 정합니다. 목표에 못 미치면 그 부분만 v4의 Java
  엔진을 별도 프로세스로 붙이는 방식(혼합)으로 바꿀 수 있게, 서버 API를 v4와 같게 유지합니다.

## 구조

- **창과 설치:** Tauri 2(MIT/Apache) + WebView2. 창, 트레이, 한 번만 실행(이미 켜져 있으면 그 창을 앞으로), 로그, 설치 파일(WiX MSI).
- **서버:** 앱 안에서 도는 Rust HTTP 서버(axum, 127.0.0.1 전용)가 **v4와 같은 `/api/v1/...` API**(지금 27개 경로)를 제공합니다.
  그래서 `frontend/`의 `api.ts`와 e2e 테스트를 거의 그대로 쓰고, 같은 e2e로 v4와 v5를 함께 시험할 수 있습니다.
- **PDF 엔진:**
  - 그리기(썸네일·미리보기·사진 내보내기·인쇄용)와 글자 위치 읽기: PDFium(BSD·Apache, 크롬의 PDF 엔진) + `pdfium-render`(MIT/Apache).
  - 페이지 조립, 내용 스트림 편집(글자 잘라 내기·다시 그리기·가림), 책갈피·입력란·링크 옮기기: `lopdf`(MIT).
  - 글꼴 읽기·고르기·심기(서브셋): `ttf-parser`, `subsetter` 등(MIT/Apache). 설치된 글꼴 색인은 v4 `SystemFonts` 동작을 옮김.
  - 암호(AES-256 걸기·풀기, 권한): 지원하는 크레이트를 찾고, 없으면 직접 구현 또는 qpdf(Apache-2.0)를 검토. 결정 필요.
  - **MuPDF는 AGPL이라 쓰지 않습니다.**
- **글자 인식:** 같은 PaddleOCR 모델(ONNX)을 `ort`(ONNX Runtime의 Rust 바인딩)로 실행. v4의 앞뒤 처리(줄 찾기·세로 글자·기울기)를 옮김.
- **그림:** `image`, JPEG/PNG 인코더(용량 줄이기·사진 내보내기·스캔 처리).
- **화면:** `frontend/`(React) 재사용, 한글 편집기 `frontend/public/hwp-studio` 그대로.
- **오픈소스 고지:** `cargo-about` 등으로 Rust 크레이트의 라이선스를 모아 v4처럼 `THIRD-PARTY-NOTICES.txt`를 자동으로 만듭니다.
  GPL·AGPL 금지(`licenses/README.md`). PDFium·ONNX Runtime 같은 C++ 라이브러리 고지도 넣습니다.
- 저장소: 같은 저장소의 새 폴더(예: `app-v5/`, Cargo 작업 공간). `backend/`(v4)는 전환 전까지 그대로 둡니다.

## 지켜야 할 것

- 화면 글자, 오류 메시지, 릴리스 노트는 모두 **한글**.
- **v4 사용자가 v5로 넘어올 수 있어야 합니다.** v4의 자동 업데이트는 릴리스의 `WINTECH_PDF_Setup_<버전>.exe`와 `.sha256`을
  받아 실행합니다. 업그레이드 코드 `{86BDF49F-B988-375C-BC21-F945E6338154}`, 데이터 폴더 `%USERPROFILE%\WINTECH_PDF`.
  - v5 설치 파일이 같은 업그레이드 코드로 v4를 교체하도록 하고(Tauri의 WiX 설정), v4 업데이트가 받을 수 있는 이름·형식으로
    올립니다. 형식이 맞지 않으면 **v4 마지막 판(다리 역할)**에서 업데이트 쪽을 고칩니다.
  - Windows 버전(`1.0.<app.version×1000>`)이 v4보다 커야 합니다.
  - v4의 작업 보관 데이터(`data\<id>.pdf` + `<id>.json`: 고친 글자·추가한 상자·그림·가림 영역·글자 인식 결과, `settings.properties`)를
    v5가 읽어 이어서 쓸 수 있게 합니다(옮기기 테스트 포함).
- 문서는 PC 밖으로 나가지 않습니다(업데이트 확인만 GitHub).
- 기능을 없애지 않습니다. 각 기능은 v4와 비교해 같거나 나아야 끝입니다.

## 단계

각 단계는 "v4 테스트를 Rust로 옮김 → 구현 → v4와 결과 비교 → 측정"으로 끝냅니다. 단계마다 무엇이 v4와 다른지 이 문서에 적습니다.

### 0단계: 기준 만들기
- v4 기능 목록(README·`docs/` 기준)과 API 목록(요청·응답 모양) 정리.
- **비교용 문서 모음:** 테스트가 만드는 PDF와 공개된 견본(엑셀·한글·워드 PDF, 스캔, 암호, 회전, Type3 글꼴, 표, 입력란·책갈피)으로
  만들고, 각 문서에 대한 v4의 출력(내보낸 PDF, 글자 목록 JSON, 썸네일, 표 선, 글자 인식 결과)을 저장해 v5와 비교하는 도구.
  실제 회사 문서는 저장소에 넣지 않습니다.
- v4 측정: 켜기, 100쪽 열기·썸네일, 내보내기, 글자 인식 1쪽, 메모리, 설치 파일 크기.

### 1단계: 뼈대 (창·설치·업데이트)
- Tauri 창 + 트레이 + 한 번만 실행 + 로그 + 설정 + 업데이트 확인, 앱 안의 axum 서버, `frontend/` 화면 띄우기.
- 켜지지 못할 때(파일 누락·포트 문제) 한글 안내 창.
- GitHub Actions에서 Windows 설치 파일 빌드(v4와 같은 방식: 작업 브랜치는 시험 빌드, 수동 실행으로 릴리스).
- **시험판은 v4와 따로 설치**되게(다른 이름·업그레이드 코드·데이터 폴더 사본) 해서 직원이 두 판을 함께 써 볼 수 있게 합니다.
- 결과: 켜기 시간·설치 크기·메모리를 v4와 비교.

### 2단계: 문서 열기와 페이지 정리
- 올리기(암호 포함), 썸네일·미리보기, 페이지 목록 조작(순서·회전·삭제·복제·빈 페이지·추출), 내보내기 조립(책갈피·입력란·링크·
  문서 정보, 내보내지 않은 페이지가 새지 않게), 이미지로 변환, 용량 줄이기, 사진으로 내보내기, 인쇄, 암호 걸어 내보내기, 작업 보관.

### 3단계: 글자 편집 엔진 (가장 어려움, 점검 지점)
- 글자 읽기(v4 `TextExtraction`의 줄 묶기·덮개 영역), 수정한 줄의 원래 글자 잘라 내기와 확인, 원래 글리프 그대로 다시 그리기
  (서브셋·Type3·CMap), 설치 글꼴로 그리기·심기, 부분 서식, 이동, 추가한 텍스트·그림, 찾아 바꾸기.
- v4의 픽셀 비교 테스트를 옮겨 같은 결과인지 확인. **여기서 품질을 보고 계속할지(또는 이 부분만 혼합할지) 사용자와 결정.**

### 4단계: 개인정보 가리기 (보안 핵심)
- 개인정보 찾기, 가림 영역, 내보낼 때 글자 실제 삭제와 두 가지 방법의 확인, 안 되는 쪽은 그림으로. v4의 가리기 테스트를 모두 통과하기
  전에는 릴리스하지 않습니다.

### 5단계: 글자 인식과 스캔 고쳐 쓰기
- 인식(같은 모델), 보이지 않는 글자층, 인식 글자 고치기, 고쳐 쓰기(바꾼 낱말만 다시 그리기, 글꼴·크기·색 맞추기, 기울기·세로 글자).
- v4와 같은 스캔에서 인식 결과·고쳐 쓴 결과 비교.

### 6단계: 나머지 기능
- 문서 비교(글자·모양), 표 선 읽기와 표 모양 복사, 글꼴 안내(.otf 등), 설정, 접속 비밀번호, 개인정보 찾기 세부.

### 7단계: 화면 정리
- 전체 버튼·메뉴·단축키 목록 → 자주 쓰는 일은 한눈에, 나머지는 묶기. 내보내기를 한 창(PDF·사진, 이미지로 변환·용량 줄이기·암호)으로.
- 디자인 시안을 먼저 확인받고 구현. 바뀐 위치를 도움말·릴리스 노트에.

### 8단계: 전환
- v4 마지막 판(필요하면 업데이트 쪽 수정) → v5를 같은 업그레이드 코드로 릴리스 → 작업 보관 데이터 옮기기 확인 → v4 코드 정리.
- 전환 전 확인: 모든 기능 목록 통과, 비교 도구에서 차이 없음(또는 사용자가 받아들인 차이만), 측정 목표 달성.

## 진행 방식

- 작업 브랜치에서 개발 → 테스트 → GitHub Actions로 시험 설치 파일(릴리스 없이) → 사용자 확인 → master 합치기 → 릴리스.
  master 합치기와 릴리스는 사용자가 요청할 때만.
- 큰 결정(암호 처리 방식, 3단계 점검 결과, 화면 시안, 전환 시점, 코드 서명 인증서)은 사용자에게 먼저 묻습니다.
- 단계가 끝날 때마다 이 문서에 결과(측정치, v4와 다른 점, 남은 일)를 적습니다.
